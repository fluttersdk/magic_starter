# Design-System Components

The 46 `MS`-prefixed components under `lib/src/ui/components/`. These carry a visual contract and nothing else: an API call, a wizard or a layout signal belongs in `lib/src/ui/widgets/` instead.

## Folder shape is fixed

Every component is a 4-file atomic folder, and a new one gets all four:

```
lib/src/ui/components/<name>/
  <name>.dart          # The widget class (StatelessWidget or StatefulWidget)
  <name>.recipe.dart   # WindRecipe: resolves className from theme tokens
  <name>.preview.dart  # Standalone preview for interactive inspection
  index.dart           # Barrel: the public API of this component
```

- Class hierarchy: `extends StatelessWidget` or `extends StatefulWidget`, NEVER `MagicStatefulView`.
- Naming: the class is `MS<Name>`, the folder and files are `snake_case`. No `MagicStarter` prefix on a component; that prefix belongs to the starter's own widgets and controllers.
- Export through `index.dart`, then through the package barrel. A component the barrel does not export is not part of the API.
- The `.recipe.dart` file holds a top-level `WindRecipe` (or a recipe function when a theme hook feeds it), so the visual contract is inspectable and testable without mounting the widget. The widget delegates className derivation to it rather than composing strings inline.

## Styling rules

- Wind UI exclusively. No Material widgets, except `Icons.*` for icon data and the Material `Dialog` shell inside `MSDialog`.
- Style through the semantic alias layer (`bg-surface*`, `text-fg*`, `border-color-border*`, `bg-primary`, `text-on-primary`, `bg-destructive`), not raw `gray-*` / `red-*` palette classes. Wind drops an unknown alias SILENTLY, so a token that does not exist renders identically to no token at all: assert the RESOLVED colour in a test, never the className string.
- The alias contract ships no destructive TEXT role. `text-destructive` parses and then resolves to nothing unless the host defines it, so resolve it with `MagicStarterTokens.role(WindTheme.maybeDataOf(context), 'text-destructive')`, which keeps a host's alias and falls back to the red pair. `MSErrorState`'s context-free icon class keeps a raw `text-red-*` pair and says so in a docblock.
- Dark mode: every colour token needs its `dark:` pair in the same className. The one exception is a class measured per build: `MagicStarterTokens.readableOn` returns a bare `text-white` or `text-gray-950`, chosen for the fill of the mode being built, and the widget rebuilds when the brightness changes.
- Never hardcode a modal className. Dialogs read `MagicStarter.manager.modalTheme` at build time (`titleClassName`, `primaryButtonClassName`, `dangerButtonClassName`, ...).

## Component-specific contracts

- **`MSCard`**: `noPadding` for full-bleed list content; `CardVariant` (`surface` default, `inset`, `elevated`) drives background, border and shadow. In `noPadding` mode the title gets `px-6 pt-6 pb-3` so it aligns with row content, and no caller adds padding around it.
- **`MSPageHeader`**: `WDiv` with `flex-col sm:flex-row`, a `border-b` separator, required `title`, optional `subtitle`, `leading`, `titleSuffix` and `actions` (rendered in a trailing `flex flex-row gap-2` row only when non-empty). `inlineActions` is `bool?` falling back to `MagicStarterPageHeaderTheme.inlineActions`, and it does TWO things that are required together: it swaps `containerClassName` for `containerInlineClassName`, AND it gives the title row `flex-1 min-w-0` instead of `sm:flex-1`. Theming the container into a row at every width without the flag leaves the title column a loose fit below `sm`, so a long title takes its intrinsic width and overflows. `MSPageScaffold` does not expose the argument, which is why the theme field exists. `className` is appended AFTER the theme's container class (`containerInlineClassName` when inline), so the last class of a family wins (`pt-0` / `lg:pt-0` takes the top padding off a header that sits under a bar of its own); it applies to `regular` and `large`, and the compact bar, whose geometry is fixed, ignores it. `MSPageScaffold.headerClassName` forwards it to the headers it builds, except the compact bar, which it builds without.
- **`MSPageHeader` title role**: the title is `Semantics(header: true)` in all three sizes (`_buildTitle`), so heading navigation finds the page title. A new title text goes through it, never a bare `WText`. The role is the only thing `MSPageHeaderHeadingScope` can take away: it is package-internal (`page_header/index.dart` does not export it, on purpose, so a host cannot strip its own page of a heading) and the large-title frame is its one user.
- **`MSPageHeader` sizes**: `size` is `MSPageHeaderSize?` falling back to `MagicStarterPageHeaderTheme.largeTitle` (`large` when set, `regular` otherwise; `compact` is never a theme default). `large` changes the title class only. `compact` is its own layout, a `NavigationToolbar` in a 44 pt `SizedBox` under a top `SafeArea`, with no subtitle and no suffixes; it blurs through a `BackdropFilter` sized by `compactBarBlurSigma` and swaps to `compactBarOpaqueClassName` with no blur when `MediaQuery.highContrastOf` is true.
- **`MSPageScaffold(largeTitle:)`**: `bool?` with the same theme fallback. The collapse needs a scroll position, so it lives here, not in the header: a private frame stacks the compact header over the scroll view and shows it once the large header's bottom edge passes under `paddingOf(context).top + compactBarHeight`, measured from the header's render box (never a fixed offset). Only `depth == 0` vertical notifications count. The bar is unmounted while fully hidden, so the title and actions appear once in the tree except while the bar shows; while it does, the large header (still partly on screen behind the bar) is wrapped in `MSPageHeaderHeadingScope(isHeading: false)`, which takes the heading role off its title and nothing else, so the subtitle the bar lacks stays readable, and while the bar fades out the bar is `ExcludeSemantics`, so the semantics tree holds one heading per visible title. Never exclude the whole large header again: that hid the subtitle.
- **Page geometry**: `MSPageContainer` carries the shared width cap, edge margins and vertical rhythm from `MagicStarter.manager.pageContainerClassName`; `MSPageScaffold` is the full page treatment (surface, own scroll, container, header, `gap-6` sections column). A component never puts a `max-w-*` or a page-level `px-*` on itself.
- **`MSDataTable`**: the default constructor renders every row; `MSDataTable.paginated` hands the body to magic's `MagicPaginatedListView` inside a box bounded by `bodyHeight` (a `ListView` needs a bound, and `shrinkWrap: true` would build every row anyway). The header stays outside the scrolling body. The component LISTENS to its paginator: reading `isEmpty` once in a stateless build only produces an empty state when the caller already awaited the first page. Column labels and `loadingLabel` are ALREADY TRANSLATED strings, not keys. The column track is a wrapper rather than a `flex-1` on the cell, so `alignEnd` applies to a flexing column too.
- **`MSConfirmDialog`**: `static Future<bool> show(context, {required title, description, confirmLabel, cancelLabel, variant, onConfirm})`. `ConfirmDialogVariant.danger` for destructive actions (delete team, revoke session), `.warning` for caution (leave team), `.primary` for neutral. The confirm button className resolves through `_resolveConfirmClassName()` against the modal theme, never a literal.
- **`MSMasterDetail`**: layout only. From `breakpoint` (`'lg'`) a `w-96 flex-shrink-0` list column and a `flex-1 min-w-0` detail column in a top-aligned row; below it `detail ?? master`. No page geometry and no scroll of its own, so it sits inside `MSPageScaffold`. Breakpoints resolve through `MagicStarterBreakpoints.isAtLeast`, which throws a `StateError` naming the setting for a name the Wind theme lacks, as the shell does.
- **`MSSegmentedControl`**: a `StatefulWidget` only for the reveal. On first mount and when `selectedIndex` changes it calls `position.ensureVisible` with the `keepVisibleAtEnd` then `keepVisibleAtStart` policies on the scroller nearest to the segment (`Scrollable.maybeOf(segment)`, any axis), after the frame, one `GlobalKey` per segment, and only when that scroller is horizontal AND either the root's own (`overflow-x-auto`) or has the control as its whole content (`maxScrollExtent + viewportDimension` within 1 px of the control's width, so a strip with padding or a sibling is the host's and is left alone). Never `Scrollable.maybeOf(segment, axis: Axis.horizontal)`: it skips a vertical list in between, and `ensureVisible` then measures against that list's viewport and jumps its vertical offset onto the strip; a page view page would be snapped mid-drag the same way. Never `Scrollable.ensureVisible`: it walks every scrollable above the segment, so the page's vertical scroll view would jump to the control or be pulled down to one below the fold. No reveal on a rebuild with the same `selectedIndex`, so the user's own scrolling stays.
- **`MSBottomSheet.show(dialogBreakpoint:)`**: from that breakpoint the call returns `MSDialog.show` with the same arguments, `scrollable` included (which is why `MSDialog` has it too). Null keeps the sheet at every width.
- **`MSDialog`**: sticky header and footer with a scrollable body (`ListView(shrinkWrap: true)`), Material `Dialog` shell around Wind content. `footerBuilder: Widget Function(BuildContext dialogContext)?` exists so a caller can `Navigator.pop(dialogContext)` with the dialog's own context.
- **Dialog footers**: compact right-aligned buttons with `justify-end gap-2 wrap`, never `flex-1` full-width. `wrap` is required alongside `justify-end`, since Wind renders it as `Wrap(alignment: WrapAlignment.end)` and a constrained container overflows without it.
- **Dialog safe area**: compute `safeHeight` from `MediaQuery.viewPaddingOf(context)`, subtract the top and bottom insets from screen height, then apply `* 0.85` for `maxHeight`. Vertical `insetPadding: 24` keeps a phone off the edges.
- **`MSTeamSelector`**: built from `MagicStarter.manager.teamResolver` callbacks. **`MSUserProfileDropdown`**: reads `MagicStarter.navigationTheme.dropdownAvatarClassName` and `dropdownAvatarTextClassName` for the trigger avatar, and listens to `Auth.stateNotifier` itself: the shell mounts it const, so it is not rebuilt when the shell is. With no name it draws a person glyph, never an initial taken from a placeholder word. The bell dropdown (`StreamBuilder<List<DatabaseNotification>>` for the live unread badge) is not one of this package's components anymore: it is `NotificationDropdown` in `magic_notifications`, mounted by `MagicStarterAppLayout._buildNotificationBell()`.
- **Team switcher and user menu panels**: every colour comes from `MagicStarter.dropdownTheme` (`panelClassName`, `dividerClassName`, `itemClassName`, `tileClassName`, `textClassName`, `mutedTextClassName`, `dangerTextClassName`, `dangerTileClassName`), never a `gray-*` literal in the widget. It is its own sub-theme because a host replaces `navigationTheme` whole after `useWindTheme()`. Both panels carry `overflow-hidden` in the widget, after the theme's classes, so a hovered row cannot paint over the rounded corners and a theme cannot drop the clip. `panelClassName` must keep a border (`border border-transparent` at the least): Wind clips a bordered box inside the border, and wraps a `ClipRRect` around the decorated container of a borderless one, which cuts off the panel's shadow. A tile's resting fill must differ from `itemClassName`'s, and a `hover:` token on the tile reacts only to the pointer being on the tile itself (a `WDiv` with one is its own anchor).
- **`MSButton`**: the recipe is `buildButtonRecipe(MagicStarter.buttonTheme)`, not a const. `shapeClassName` sits where `rounded-lg` was in the base; `smClassName` / `mdClassName` / `lgClassName` carry padding, minimum height and label type of a size; `secondaryBorderClassName` is the one colour field, since a border costs layout (`''` drops it; `border-0` paints a hairline). Colours stay in the recipe as semantic aliases, so `useWindTheme()` derives nothing and resets the theme. Its own sub-theme, because a setter assigns the whole struct. The default theme must keep emitting the previous classNames byte for byte (a test pins all 12). Below `lg` the 44 px hit area wraps every size and adds nothing to one that is already 44. A 44 px size is `py-[11px]` plus `leading-[22px]`, never `min-h-11` alone (Wind gives the box a minimum height and no alignment, so the label sits at its top). A caller `className` is appended after the theme and wins on any family it names. The form and auth theme button strings (`formTheme.primaryButtonClassName` and `secondaryButtonClassName`, `authTheme.guestButtonClassName`) therefore carry NO `rounded-*`, `py-*`, `text-<size>` or `border-*` token: the auth views hand the primary to an `MSButton` of `ButtonSize.lg` and the social, guest and step-up provider buttons to a `ButtonIntent.secondary` one of `ButtonSize.md`, and the geometry and the secondary border come from the button theme (a `border-*` colour token alone paints a hairline in Wind, so it cannot stay in a string). The strings keep `w-full`, the colours, `font-semibold` on the primary and `hover:opacity-90` on the secondary ones (the opacity the buttons had while they borrowed the primary intent). A host that sets its OWN form or auth button strings keeps whatever geometry it wrote (it changes one string with `MagicStarter.formTheme.copyWith(...)`, since `useFormTheme` assigns the whole struct); the dialogs and the team settings invite button use raw `WButton`s on the modal theme and never read the button theme.
- **Form controls (`MSInput`, `MSSelect`, `MSCombobox`, `MSSegmentedControl`)**: the padding, minimum height and type are `MagicStarter.fieldTheme` (`MagicStarterFieldTheme`), its own sub-theme because a setter assigns the whole struct and `useWindTheme()` / `useTheme()` reset it. `inputRecipe` is `buildInputRecipe(theme)`, and `selectRecipe`, `comboboxRecipe` and `segmentedControlRecipe` take `theme:`, which the widgets fill from the facade; each field REPLACES one run of tokens in its recipe, so the side padding (`px-3`), colours and border stay outside it. The default theme must keep emitting the previous classNames byte for byte (a test pins all of them), with ONE exception: the input's `text-fg` moved ahead of the size run (`px-3 text-fg py-3 lg:py-2.5 text-sm leading-5`) so the run is contiguous, which parses to the same style (a test compares the two). The placeholder inherits the field's type, so there is no placeholder field. 44 px is padding around a fixed `leading-*`, and the numbers differ per control: `WInput` paints its border inside the padding (`py-[11px]` around 22 is 44, `py-2.5` is 42), a `WSelect` trigger adds it (`py-2.5` is 44). `MSSegmentedControl` needs `segmentedPaddingClassName` (`px-1 py-0 lg:py-1`) for a 44 px control below `lg`, where the 44 px hit cell plus the default `p-1` root is 52 px; the `hit` slot is the touch target and is never themed. `MSSelect`, `MSCombobox` and `MagicStarterTimezoneSelect` share `selectSizeClassName`. A caller `className` / `classNames` is appended after the theme and wins. The auth, profile and settings forms use `WFormInput` on the form theme's `inputClassName` (with its own `py-3`) and are outside this theme, as are the starter's own `WFormSelect`s (team settings role, profile language, language preference), whose trigger reads the same string (a host changes it with `MagicStarter.useFormTheme(MagicStarter.formTheme.copyWith(inputClassName: ...))`). One `py-*` cannot make an input (border inside the padding) and a select (border added) both 44 px; `py-[10px] min-h-11 text-[17px] leading-[22px]` does.
- **`MSToast`**: the message is `kToastMessageClassName` (`text-sm font-medium`) and an optional `messageClassName` is appended after it (last wins), on the `WText` only and with or without an action; the default MESSAGE className is pinned byte for byte. Presentational only; the host's overlay decides how long it shows and what pressing the action does. `Magic.toast(String)` takes a message and a duration, no widget, and its overlay is an `IgnorePointer` (`magic_feedback.dart`), so an action is only reachable when the host presents the `MSToast` through its own `OverlayEntry`; never document `Magic.toast()` as the way to show one. `actionLabel` and `onAction` (both or neither, an assertion) add a trailing text action, two plain parameters as on `MSUpdateBanner` rather than a value class, so the pair adds no type to the API. Without one the tree is the old single-child `WDiv` and the `info` recipe output is the old string, pinned byte for byte (the three toned variants read the on-colour role of their fill where they had a literal `text-white`, so their string differs on purpose); a message-only toast still does not wrap, so a long message overflows a narrow row there. With one, the box takes `kToastWithActionClassName` (`py-0 px-2`, symmetric, never a physical `pr-*`, so a right to left toast keeps the same edge distances) ahead of the caller's className, the message column takes the rest (`flex-initial min-w-0 px-2 py-3`: a loose fit, so short text shrink-wraps and a long one wraps beside the action), and the cell (`toastActionRecipe`) is `min-h-11 min-w-11` inside a `WAnchor` with `semanticLabel: actionLabel`. The label is centred in it with `Center(widthFactor: 1, heightFactor: 1)`, which is the label's size raised to the cell's minimum: a `flex-col` cell grows to the whole height an overlay offers it (844 px in a bounded parent; the same defect `MSSegmentedControl`'s hit cell has), and a fixed `h-11` overflows at a large text scale (a test pins 2.5). Its focus ring is `ring-inset`, because the cell is as tall as a one line toast and an outside ring would paint beyond the box. The info tone reads `text-primary` with a `bg-surface-container-high` hover. The three coloured tones read the ON-COLOUR ROLE of their fill for the container text (so the message), the label, the ring and the hover fill, never a literal `text-white`: `text-on-success`, `text-on-warning`, `text-on-destructive`, resolved through `MagicStarterTokens.readableOn(context, fill:, role:)`: a role the host DEFINES is returned as written; one it does not is not assumed to suit the stock fills (a host may redefine `bg-success` as a dark green), so the fill is resolved in the current brightness and the better of `text-white` and `text-gray-950` by WCAG contrast is returned (the stock green and amber get near-black), and with no fill to measure the answer is `role()`'s fallback pair (`text-on-success` and `text-on-warning` are role fallbacks, not alias keys, near-black `gray-950`). A translucent fill is measured over `bg-surface`. A ring takes a colour and not a text role, so the ring and the `hover:bg-[#hex]/15` fill are made from the colour the measured class paints now (`WindParser.parse(onClassName, context).color`, `onClassName` being what `readableOn` returned); `buildToastRecipe` therefore takes the active `WindThemeData` and that `onClassName`, and a host calling it directly without the class gets the role's fallback pair, not the measured one. A test measures 4.5:1 for the text and 3:1 for the ring off the rendered colours under a host that defines the roles. The recipe file's `index.dart` shows only `buildToastRecipe` and `kToastVariantAxis`.
- **`MSSocialDivider`**: `WDiv` + centred `WText('or')`, used between a form and the social login buttons.
- **`MSFormActions`**: the cancel/submit footer row for a form; `submitLabel` and `isSubmitting` are required, `cancelLabel`/`onCancel` are optional (null renders no cancel button). Wraps (`wrap`) rather than stretching, since a full-width `MSButton` hands the row an unbounded child.
- **`MSSwitchRow`**: a full-width `MSSwitch(label:)`. The switch lays its label out itself (a two-slot render box, not a flex row, so it works in an unbounded-width row and under `IntrinsicHeight`): the label wraps in the width beside the track, toggles the switch when tapped, and is its accessibility name. A one-line label sits on the track's centre line, a wrapped one aligns to its top. The row's className can be overridden by a caller; the label layout cannot.
- **`MSHeaderAction`**: a page-header action that collapses to an icon-only glyph below `lg` and a labelled `MSButton` at `lg` and up; `label` becomes the icon form's accessibility label rather than being dropped.
- **`MSKeyValueEditor`** / **`MSKeyValueRow`**: controlled editor for an ordered list of key/value pairs (e.g. HTTP headers); every mutation emits a fresh list via `onChanged`, never mutating `value` in place.
- **`MSStringValueList`**: controlled editor for a short list of distinct strings, rendered as `WBadge` chips; commits on Enter/IME-done, trims and case-insensitively de-duplicates before appending, and Backspace on an empty draft drops the last chip.
- All five take every visible string as a required constructor parameter (no `cancelLabel`/`onCancel` pair, which is optional): none reads a translation key of its own.

## Sizing and tree-shaking

- `MSButton`, `MSInput` and `MSTextarea` take `bool fullWidth = false`. It wraps the rendered widget in a `SizedBox(width: double.infinity)` rather than adding a className token, because Material widgets ignore cross-axis stretch (flutter/flutter#19399).
- `Icons.*` in a `build()` goes to a `static const _iconName = Icons.xxx` field. Flutter web cannot tree-shake icons referenced inline.
